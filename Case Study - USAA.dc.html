myTM — a headless ATM you unlock from your phone

Designing the iOS app behind a QR-connected ATM concept — no card slot, no keypad — balancing offline convenience with security-by-design.

Client — HCL Role — UI Designer Platform — iOS, 2014
Cash transactions moved off branch staff onto self-service
Every transaction can be built and saved fully offline
No screen ever reveals a machine's cash contents
The Concept — a Headless ATM

The bank wanted to cut branch traffic for simple transactions — withdrawals, deposits, check deposits — without building more ATMs with screens and keypads. Their answer was a "headless" machine: just cash slots and a QR code above it. The phone became the interface; the machine became a dumb dispenser that only did what the phone told it to.

That handed the entire experience to the app. Every decision a physical ATM UI normally makes — amount, denomination, confirmation, error handling — had to happen on-screen, before or after the user ever stood in front of the machine.

Designing for Offline-First

Nothing about setting up a transaction should require standing at the machine. Users pick withdraw or deposit, enter an amount, choose specific bills if it matters to them, and save the transaction — all from home, on their own time. The machine only comes into play at the very last step, to scan and execute.

Choosing Denominations, Without Tipping Off the Machine

Beyond a flat amount, users can specify exactly which bills they want — how many $100s, $50s, $20s — before ever reaching the machine. We never showed which denominations the machine actually had loaded, or how many. If a user asked for bills the machine couldn't fulfill, we only told them at the point they tried to save or execute — never upfront — so the interface never leaked what cash was sitting inside an unattended machine.

Denomination availability is never shown in advance — a deliberate security constraint, not an oversight.

Cash and Check Deposit

Deposits worked the same way in reverse — set the expected amount from the app, then feed cash or a check into the machine to match it. If a user inserted more or less than declared, the app and machine reconciled the difference, with the correction surfaced back on screen once the transaction completed.

Security by Design

A headless machine only works if compromising the app doesn't compromise the money. We kept a checklist of scenarios where the interface could accidentally leak information to an attacker, and wrote them out of the flow before they shipped.

Generic Errors No Cash Disclosure QR-Scoped Sessions Locked Mid-Transaction

Generic login errors

A failed sign-in never states whether the username or the password was wrong — only "username or password is incorrect" — so a stolen device can't be used to enumerate valid accounts.

No cash-on-hand disclosure

Denomination availability inside a given machine is never surfaced in advance — the app confirms feasibility only at save or execute, never as a browsable inventory.

QR-scoped connection

Scanning the code above the machine is what binds the app session to that one physical unit — a saved transaction can't execute on an arbitrary machine it wasn't pointed at.

Locked mid-transaction

Once a transaction is in progress at the machine, the connection toggle disables — no second device can pair with a machine that's actively dispensing or accepting cash.

The QR code above each machine — scanning it is the only way to connect a session to that unit.

Reflection

This was the first project where I had to design against an adversary, not just a confused user. Every screen needed a second read: not "is this clear," but "what does this reveal if the wrong person is holding the phone." That discipline — treating omission as a design decision — has stayed with me on every banking project since.
